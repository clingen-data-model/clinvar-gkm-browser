## 1. How to run it

### 1.1 Inputs the fork needs [code]

| Input | Where the code expects it | Notes |
|---|---|---|
| **New-format RCV XML**: `ClinVarRCVRelease_YYYY-MM.xml` (or `_00-latest`), uncompressed | any path, passed as argv to `import-clinvar-xml.py` | From `https://ftp.ncbi.nlm.nih.gov/pub/clinvar/xml/RCV_release/`. The latest file, `ClinVarRCVRelease_00-latest.xml.gz` (= 2026-10), is **6.29 GB gzipped**, ReleaseSet `Dated="2026-09-28"`, schema `ClinVar_RCV_2.3.xsd`. The importer does **not** read the VCV release. It parses `<ClinVarSet>` → `ReferenceClinVarAssertion` + `ClinVarAssertion/Classification/{GermlineClassification,SomaticClinicalImpact,OncogenicityClassification}`. |
| `mondo.owl` | **cwd** (`Mondo('mondo.owl')`) | `make mondo` gets it from purl.obolibrary.org. It is 255 MB (v2026-10-06). It is loaded at import time only. |
| `submitter_info.tsv` | cwd, committed in the repo | org ID → name → ISO3 country. It is regenerated by `make countries` (`get-submitter-info.py`, which needs `organization_summary.txt` and scrapes NCBI submitter pages). The committed copy (updated 2026-10-21) was used as-is. |
| `nonstandard_significance_terms.tsv` | cwd, committed | term normalization map |
| `organization_summary.txt` | cwd | only used by `get-submitter-info.py`. I downloaded it (0.9 MB) but didn't need it. |

Other requirements [code + obs]:
- **Python ≥ 3.12.** `sqlite3.connect(..., autocommit=False)` was added in 3.12. My first venv was 3.10 and would have failed.
- Python packages: cachelib, flask, html5lib, psutil, pycountry, tqdm, zstd.
- The app must run with **cwd = repo root**. It opens `clinvar.db`, `nonstandard_significance_terms.tsv` and the templates relatively.

### 1.2 Exact steps I ran

```bash
git clone https://github.com/alexhenrie/clinvar-miner clinvar-miner-fork     # HEAD 2a63bb1
cd clinvar-miner-fork
uv venv --python /opt/homebrew/bin/python3.12 .venv
uv pip install --python .venv/bin/python -r requirements.txt                       # .venv = 29 MB
mkdir data-local
curl -sL -o data-local/mondo.owl http://purl.obolibrary.org/obo/mondo.owl          # 255 MB, ~10 s
ln -s data-local/mondo.owl mondo.owl                                               # code wants it in cwd (gitignored)
# build the subset (section 1.3) -> data-local/ClinVarRCVRelease_subset.xml (368 MB)
.venv/bin/python import-clinvar-xml.py data-local/ClinVarRCVRelease_subset.xml     # 56 s wall, ~545% CPU
.venv/bin/python create-indexes.py                                                 # 16 s
FLASK_APP=clinvar-miner.py TTL=-1 .venv/bin/flask run -h 127.0.0.1 -p 5051         # same as start-dev.sh minus debug
```

I skipped `prune-old-clinvar-versions.sh` because the DB held one date. I made **no code changes**. The only local tweak is the `mondo.owl` symlink.

### 1.3 Building a small but conflict-rich subset

**What I tried first: the head of the bulk file.** I streamed the first 400 MB uncompressed of `ClinVarRCVRelease_00-latest.xml.gz` and found it nearly useless [obs]:
- It held 32,288 ClinVarSets with only 32,624 SCVs, about one SCV per RCV.
- At most 5 submissions on any RCV, and only 147 sets were "conflicting".
- The file is **not ordered by RCV or variation ID**. It starts at RCV000019898 and looks like ClinVarSet-ID (update) order. Low variation IDs are not near the top.
- A variant's several RCVs are scattered across the file. ClinVar Miner compares SCVs across all RCVs of a variant (`JOIN ON variant_name`), so a head slice also breaks comparisons.

I deleted that sample.

**What I used: NCBI E-utilities, gene-targeted, all RCVs per variant.** The script (esearch, then esummary for RCV accessions, then efetch of the ClinVarSet records; not kept in the repository) ran with system `python3 -I`, standard library only.
1. `esearch db=clinvar term="<GENE>[gene]"` (optionally `AND clinsig_has_conflicts[prop]`) gives variation IDs.
2. `esummary retmode=json` gives `supporting_submissions.rcv`, which is every RCV of each variant.
   - esummary refuses JSON over 10 MB, which happened on G6PD's large CNVs. The script bisects the batch on that error.
3. `efetch db=clinvar rettype=clinvarset id=RCV…` (200 per call) returns **the same new RCV-format `<ClinVarSet>` elements** as the bulk file.
   - It works with RCV accessions only. Variation IDs return an empty set.
   - The data is live (records updated 2026-10-24), so I wrapped them in `<ReleaseSet Type="full" Dated="2026-10-24">`.
4. Genes used:
   - all variants in HFE, GJB2, SERPINA1, MEFV, PAH and G6PD
   - 400 conflicting MYH7 variants and 300 conflicting BRCA2 variants
   - all RCVs of three somatic hotspots (KRAS G12D var 12582, BRAF V600E 13961, TP53 R175H 12374). The germline genes had **zero** Somatic/Oncogenicity classifications, so I added these to exercise the fork's somatic handling.
5. Result: 12,696 ClinVarSets, 367.7 MB XML, valid (checked with iterparse). E-utilities time was about 8 minutes, plus one failed attempt before I added the bisecting.

Total downloaded was about 1.05 GB: the discarded 400 MB uncompressed stream (much less compressed), 370 MB from E-utilities, 255 MB of Mondo and 1 MB of org summary.

### 1.5 Problems hit

1. **Python 3.10 venv**: `autocommit=` needs 3.12+. I recreated the venv on 3.12.
2. **The bulk-file head is unrepresentative**: see 1.3.
3. **esummary JSON 10 MB cap** on big CNV batches: fixed by bisecting in my script.
4. **HTTP 406 unless the request advertises zstd** [obs + code].
   - `before_request` aborts when `zstd` is missing from `Accept-Encoding`, even in dev mode where nothing gets compressed.
   - `curl` with no header gets 406. Playwright's Chromium sends zstd on plain `http://127.0.0.1` and works.
   - Older browsers, scripts or crawlers without zstd are refused outright.
5. `/total-submissions-by-country/` (blank code, "unspecified") returns 404 here, because every submitter in the sample has a country.
6. No server errors (5xx) in `data-local/app.log` across about 160 requests. Pages took 0.5 to 1.4 s each on this small DB.

The app is stopped and nothing is left running. The clone of upstream eilbecklab/clinvar-miner (`eb7da45`) was not touched.

What is left on disk:
- `clinvar-miner-fork/clinvar.db` (647 MB), `.venv`, and `mondo.owl` → `data-local/mondo.owl`
- `data-local/`, 608 MB: the subset XML, mondo.owl, org summary, logs and per-gene RCV caches

## 2. Fork vs the old upstream clone

Upstream eilbecklab/clinvar-miner at `eb7da45` (2024-02-15) is a direct ancestor of the fork. The fork has **23 commits** since then, 2026-01-16 to 2026-10-23, all by Alex Henrie. `git diff --stat`: 18 files, +1263 / −429. About 1,186 of those lines are `submitter_info.tsv`.

### Data and import
- **New-format RCV XML only** (`7887147`, 2026-06-21).
  - Downloads move from `RCV_xml_old_format/ClinVarFullRelease_*` to `RCV_release/ClinVarRCVRelease_*`.
  - The old-format fallbacks are removed (missing OrgID→500139 "ClinVar Staff", missing variant name, blank genes, missing review status and method). The importer now assumes every element exists.
  - The historical import loop now starts at 2024 instead of 2012.
- **Germline/somatic flattening** [code + obs].
  - Each SCV's `significance` is one string: GermlineClassification if present, else SomaticClinicalImpact, else OncogenicityClassification, else "not provided".
  - The schema adds no column for classification type, somatic assertion type (diagnostic or prognostic), or clinical-impact significance.
  - `nonstandard_significance_terms.tsv` maps "tier i - strong" → pathogenic, "tier ii - potential" → likely pathogenic, "tier iii - unknown" → VUS, "oncogenic" → pathogenic and "likely oncogenic" → likely pathogenic.
  - **Observed effect** on KRAS G12D: somatic "Tier I - Strong" vs germline "Pathogenic" is stored as a *synonymous conflict* (level 1, 256 pairs). Somatic "Tier II - Potential" vs germline "Pathogenic" is a *confidence conflict* (level 2, 96 pairs). "Variants by significance → pathogenic" silently includes somatic Tier I and oncogenic SCVs.
  - These pairs mostly have `normalized_conflict_level = -1`, i.e. different Mondo conditions (cancer vs RASopathy), so the default view hides them. "Report conflict between different conditions" exposes them.
- Significance map rewritten: 34 → 20 entries. Many old free-text terms are gone (vus, vous, probable-pathogenic …), presumably because ClinVar now normalizes them. Added: low-penetrance terms, risk-allele terms, vus-high/mid/low, tier I–IV, oncogenic and likely oncogenic.
- Import is always parallel (`Pool().imap_unordered` over a regex generator). The RAM check (psutil) is gone, though psutil is still in requirements. Everything runs in one transaction (`autocommit=False`) so readers never see a half import.
- `create_tables()` now commits before the import starts (`3330b69`).

### Web app
- **Responses compressed with zstd, now mandatory** (`9de1cbc`). The cache stores zstd bodies, and requests without zstd get 406 (see 1.5).
- **The "Significance terms" page is removed** (route commented out, `ada11b8`). `/significance-terms` returns 404 [obs].
- The search fallback goes to **Brave** `site:` search instead of Google.
- The date selector is hidden when the DB holds one release (`8d298d1`).
  - In normal operation `prune-old-clinvar-versions.sh` keeps only the latest release, so **the release filter is effectively gone**.
  - With 2 releases it reappears as a "ClinVar version" `<select>` next to "Apply filters" on every page with a filter form [obs, `A2`–`A5`]. It is absent from the home page and the Mondo index.
- Query builder refactor (`and_optimized_filters`, `2a63bb1`). Star filters are applied only when > 0, and the `conflict_level=-1` self-pair shortcut is used when no comparison is needed.
- Ties in count-sorted tables are now sorted alphabetically (`60af45e`).
- Branding: Utah/NCBI/ClinGen logos commented out, StatCounter and Google site verification removed, disclaimer reworded. Source link now points to the fork.
- "Super-escaped" condition names in breakdown links (`126c3a9`, `superescaped_base_url()`): fixes conditions containing "/".
- **No new pages or features.** The page set is upstream's minus the significance-terms page. There is still one release in practice, no API, and no over-time graphs (those were already commented out upstream before Feb 2024).

## 3. Page-by-page inventory (from the running app)

### Common UI on every page [obs]
- **Header:** global search box ("Search by gene, HGVS, rsID, etc.").
- **Filter form** (a subset per page, see each page):
  - Minimum review status: blank (any), 1★, 3★ or 4★. There is no 2★, because SCVs never have it.
  - Collection method: clinical testing, curation, literature only, research, other.
  - Minimum conflict level: 0–5.
  - "Report conflict between different conditions" (`original_conflict_levels`).
  - Gene type: single gene / close-or-overlapping / large variant.
  - "Distinguish antisense genes from sense genes" (`original_genes`).
  - "Show significances as they were submitted" (`original_terms`).
  - "Apply filters" submits a GET, so every view is a shareable URL.
- **Two-sided filters on conflict pages.** The labels change with context:
  - "Y axis … / X axis …" on significance and gene conflict pages.
  - "submission from <Lab> / the other submission" on submitter pages.
  - "submission for <condition> / the other submission" on condition pages.
- **Tables:**
  - client-side sortable (tablesorter)
  - "Search this table": a substring filter on the first meaningful column. It is disabled ("Please wait…") until the JS loads.
  - "Download table as spreadsheet": client-side CSV of the table
  - "#" anchors on h2 headings
  - every table on a page is unpaginated
- **Colour key for conflict cells:**
  - level 0 green
  - level 1 light green
  - level 2 yellow
  - level 3 light orange
  - level 4 orange
  - level 5 red/pink
  - totals pale yellow
- **Conflict overview row**, at the top of every conflict page. Its columns:
  - "Variants with only 1 submission per condition"
  - "≥2 submissions on the same condition and no conflicts"
  - levels 1–5
  - "Variants with any conflict"

  Above it is a note that a variant may be counted in several columns. If you set a minimum conflict level, the columns below it collapse into "no conflicts below the specified minimum level". If you tick cross-condition, the labels drop "per condition".
- External links (small icon): NCBI variation, RCV and submitter pages; MedlinePlus Genetics (ghr.nlm.nih.gov) for genes; dbSNP; Monarch/MedGen/OMIM/Orphanet/HPO/MeSH/etc. for condition xrefs.

## 4. Assessment for curators

### Most useful (keep and improve)
1. **Lab-vs-lab conflict pages** (`88`, `89`, `90`). This is the standout.
   - From one lab, the "submitter to submitter summary" ranks every other lab by disagreement, by level. One click gives the head-to-head term × term matrix, and one more gives the variants in a given cell.
   - Combined with the other-side filters (`min_stars2=3` = vs expert panels, `method2=curation`), a lab can ask "where do we disagree with VCEPs?" in two clicks (`88b`).
   - Nothing on NCBI does this.
2. **The per-lab conflict scorecard** (`87`) and the **significance × significance matrix** (`80`, and per gene `83`).
   - The matrix shows at a glance whether a gene's conflicts are P/LP-vs-VUS (actionable) or B/LB-vs-VUS.
3. **Graded conflict levels with a same-condition default.** Separating confidence conflicts (P vs LP) from clinically significant ones (P/LP vs VUS/B) is what curators triage on. The "different conditions" toggle is a useful second lens.
4. **Pivot plus drill-down with filters preserved**: gene/condition/submitter × significance tables leading to variant lists leading to the variant page. Every view is a URL, and multi-select works (`20c`, `50b`, `82b`).
5. **The Mondo roll-up** (`41`): seeing "cardiomyopathy" across 23 ClinVar condition strings is valuable. The condition-to-condition summary (`86b`) shows how one disease is fragmented into "not provided", "PAH-related disorder" and so on.

### Weak or misleading (fix in this app)
- **Conflict variant lists don't show the conflict.** Every list is HGVS, dbSNP and gnomAD only, with no per-side term, submitter, stars or date. Curators have to open each variant.
- **Germline, somatic and oncogenicity are mixed in one scale** [obs]: somatic Tier I vs germline P counts as a "synonymous conflict", and P/LP counts include somatic and oncogenic SCVs. We should keep the three classification types separate.
- **Flagged submissions are counted** [obs]. 59 SCVs with review status "flagged submission" get star 0 and take part in 911 level-5 pairs; ClinVar excludes them from aggregates. "No classification provided" becomes "not provided" and so is never in conflict.
- **"not provided" / "not specified" conditions all map to MONDO:0000001** [obs]. With the default same-condition comparison, a lab saying Pathogenic for "not provided" is never compared with a lab saying Benign for "Hereditary hemochromatosis" (H63D: 19 root-mapped SCVs vs 38 MONDO:0021001). This undercounts conflicts unless you tick cross-condition.
- **Variant identity is the HGVS name string**; there are no VCV, VRS or ClinGen allele IDs. Large CNVs become giant "gene combination" rows (245k-px page).
- **Exact-string condition matching** on submitter × condition (`54` returned 0).
- **No VCV/RCV aggregate classification**, no SCV dates beyond last-evaluated, no history or diff (one release in practice), no API, CSV only from the rendered table, no pagination.
- **zstd-only HTTP** (406 otherwise) blocks scripts and older clients.
- The Mondo index has no counts, no hierarchy and no filters.
- Multi-condition submissions appear as long "; "-joined condition names.

### Not in our earlier notes (`docs/research/clinvar-miner-and-landscape.md`, `docs/features.md`)
- "Total variants **unanimously** reported as <sig>" on the significance pages.
- `/variants-in-conflict-by-submitter/<id>/0` = "<Lab> vs any submitter" (`89b`). The notes mention `id2=0`; it is confirmed working.
- Context-specific two-sided filter labels ("Y axis/X axis", "submission from <Lab>", "submission for <condition>").
- When a minimum level is set, the overview row collapses lower levels into "no conflicts below the specified minimum level".
- The condition-conflict matrix cells are not drill-down links, and an orphan `variants-in-conflict-by-condition--2significances.html` template exists with no route.
- The min-stars options are any/1/3/4 (no 2★ at SCV level); gene type 0 (intergenic) is not offered in the UI.
- zstd is mandatory (406), the Brave fallback, and the date selector hidden with one release.
- Flagged-submission inclusion, the "not provided" → MONDO:0000001 behaviour, and the somatic-to-germline term mapping, all seen in the DB.
- The new RCV XML bulk file is not sorted by accession or variation ID, so head-sampling it doesn't work. E-utilities `efetch rettype=clinvarset id=RCV…` returns the same new-format ClinVarSets and is a cheap way to build test fixtures (useful for our own CI).
- Sizing: 20k SCVs → 233k comparison rows → 647 MB indexed SQLite; a second release doubles it (1.38 GB). This supports the earlier inference that multi-release history was dropped for size.
